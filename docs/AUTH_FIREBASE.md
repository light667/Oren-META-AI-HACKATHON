# Connexion Firebase reliée à Supabase (2026-11-06)

Pourquoi : les liens magiques Supabase (SMTP intégré) étaient limités en envoi. Firebase gère désormais l'identité : e-mail + mot de passe, e-mail de vérification, mot de passe oublié, Google. Supabase garde toutes les données et la RLS.
Fonctionnement : le navigateur se connecte à Firebase puis envoie son jeton à `POST /api/auth/session` ([route.ts](/src/app/api/auth/session/route.ts)). Le serveur vérifie la signature Google, le projet et l'e-mail vérifié ([verify-token.ts](/src/lib/firebase/verify-token.ts)), relie le compte Firebase à **son** compte Supabase (table `auth_identities`, créé au besoin, retrouvé par e-mail pour les comptes existants et les invités, [auth-bridge.ts](/src/lib/auth-bridge.ts)), puis ouvre la session Supabase par jeton à usage unique **sans aucun e-mail Supabase** (`generateLink` + `verifyOtp`, vérifié en réel). La RLS (`auth.uid()`), `staff` et `businesses` sont inchangés. Les invitations ne passent plus par Supabase : compte préparé + e-mail Resend vers `/inscription?invitation=1`.
Mise en place (manuel, une fois) : 1) Console Firebase > Authentication : activer « E-mail/Mot de passe » et « Google » ; Settings > Authorized domains : ajouter le domaine de prod. 2) Copier la config Web dans les variables `NEXT_PUBLIC_FIREBASE_*` (local et Vercel). 3) Supabase > SQL Editor : exécuter `supabase/migrations/20261106000100_firebase_identities.sql`.
Essayer : `/inscription` → e-mail de vérification Firebase → la page continue seule une fois le lien cliqué → `/bienvenue` puis l'espace patron. `/connexion` : mot de passe ou Google. Les comptes Supabase existants retrouvent leur entreprise en créant leur mot de passe avec la même adresse.
Tests : `verify-token.test.ts` (signature, projet, expiration), `auth-bridge.test.ts` (un compte Supabase par compte Firebase, pas de doublon, pas de fusion), `tests/db/auth-identities.test.ts` (table et fonction réservées au service_role).

## Choix du mode : mot de passe + e-mail de vérification, pas de lien de connexion (2026-11-06)
D'après https://firebase.google.com/docs/auth/limits (plan gratuit Spark) : 1 000 e-mails de vérification par jour, mais seulement **5 e-mails de connexion par lien par jour** (25 000 avec le plan Blaze, donc avec facturation). La connexion par lien seul recréerait la limite qu'on quitte. Retenu : mot de passe + vérification d'e-mail (un seul e-mail à l'inscription, aucun à la connexion) + Google. Le lien de connexion reste ajoutable plus tard si le plan Blaze est activé.
Vérifié en réel sur le projet `ai-oren` : inscription → compte Firebase créé et e-mail de vérification envoyé ; `/api/auth/session` avec un vrai jeton non vérifié → 403 `email_not_verified` (signature Google contrôlée) ; jeton falsifié → 401 ; compte de test supprimé. `localhost`, `ai-oren.firebaseapp.com` et `ai-oren.web.app` sont autorisés ; **le domaine de prod reste à ajouter**. Non vérifié ici : le passage final vers la session Supabase (il faut cliquer un vrai lien reçu, et la migration `20261106000100_firebase_identities.sql` doit être appliquée) et la connexion Google (fenêtre popup).

## E-mails Firebase : page d'action Oren et délivrabilité (2026-11-06)
Constat : l'e-mail de vérification arrivait en spam, signé « project-752675618 », expédié par `noreply@ai-oren.firebaseapp.com` (domaine partagé Google), lien Google brut. Le projet n'a **aucun domaine à soi** (rien sur Vercel ; `EMAIL_FROM` Resend en `resend.dev`, adresse de test qui n'écrit qu'au propriétaire du compte, aucun domaine vérifié chez Resend).
Fait dans le code : page d'action hébergée par Oren, [`/auth/action`](/src/app/auth/action/page.tsx) ([auth-action.tsx](/src/components/auth-action.tsx)) : vérifie l'adresse puis ouvre directement l'espace (même navigateur), gère le nouveau mot de passe (puis connexion automatique), l'annulation de changement d'adresse et les liens expirés, au design Oren, FR/EN. `/bienvenue` rendue explicitement dynamique (`connection()`).
À faire dans la console Firebase (sans code) : 1) Paramètres du projet > Général > **Nom public** = « Oren » (remplace « project-752675618 »). 2) Authentication > Templates > Vérification de l'adresse e-mail : nom d'expéditeur « Oren », objet « Confirmez votre adresse e-mail Oren », langue française ; **Personnaliser l'URL d'action** = `https://<domaine-prod>/auth/action` (ou `http://localhost:3000/auth/action` en local). 3) Avec un domaine à soi : Templates > Domaine personnalisé (enregistrements DNS SPF/DKIM) — c'est ce qui sort réellement du spam. Étape suivante possible une fois le domaine vérifié chez Resend : e-mails HTML entièrement à la charte, envoyés par Oren.
Essayer : `/auth/action?mode=verifyEmail&oobCode=x` affiche « Lien invalide ou expiré » ; un vrai lien (après l'étape 2) vérifie et entre dans l'espace.
