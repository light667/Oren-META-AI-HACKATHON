# Tableau des commandes, conversations et alertes (2026-10-30)

Commandes en temps réel (Supabase Realtime, migration `20261030000400_order_alerts_push.sql`) : statuts `pending` (brouillon client) → `confirmed` (« Reçue ») → `accepted` (« Acceptée ») → `preparing` → `ready` → `delivered`, `cancelled` possible avant « prête » ; la machine à états `src/lib/order-transitions.ts` refuse toute autre transition (409), et l'acceptation enregistre `accepted_at` — le délai d'acceptation est affiché. Sur le projet distant déjà initialisé, exécuter la section 4/5 de `supabase/apply_all.sql`.
Alertes via `NotificationProvider` : temps réel + son dans le tableau patron à l'arrivée, vraie notification Web Push (service worker `public/sw.js`, abonnements `push_subscriptions`, clés VAPID à mettre dans `.env`), et e-mail de secours si la commande n'est pas acceptée après le délai réglable (défaut 3 minutes, réglable par entreprise dans « Mon entreprise », e-mail via Resend si configuré). Déclenchement de cet e-mail : cron externe gratuit toutes les minutes (cron-job.org), car le cron Vercel gratuit est limité à une fois par jour — voir `docs/ALERTES_CRON.md`.
Conversations : boîte de réception avec filtre « À reprendre », fil en temps réel ; répondre met l'assistant en pause sur ce fil jusqu'au bouton « Rendre la main à l'assistant ». Le bouton « Couper l'assistant » (même écran, `config.assistant_enabled`) arrête le modèle immédiatement pour toute l'entreprise et transmet à un humain. Côté client, le statut de sa commande se met à jour à l'écran sans recharger (vérification légère par sa session).
Paiement : « payer à la livraison / sur place » et faux fournisseur de test restent derrière `PaymentProvider`, avec tests. Pour l'essayer : commander depuis `/chez-chef-t`, regarder le tableau patron sonner, accepter, et suivre le statut côté client.
Critère mesuré en réel le 2026-10-31 (Chrome, deux contextes : cliente sur la vraie page publique avec le vrai modèle, patron connecté sur le tableau ; entreprise de test ensuite supprimée, distant à 32/32) : commande 2 attiéké + 1 jus livrés à Agoè = 5000 FCFA, confirmée par le bouton ; **apparition chez le patron en 494 ms** via Realtime (critère : moins de 2 s), **son déclenché 1 fois** (oscillateur Web Audio compté dans la page), clic « Accepter » du patron, **statut « Acceptée » revenu à l'écran de la cliente sans rechargement** (marqueur de page intact), **délai d'acceptation enregistré en base : 3 184 ms** (`accepted_at - received_at`). Client stocké avec `phone_verified_at` vide.
Trois bugs réels corrigés grâce à cette mesure : la session anonyme cliente résolue pendant le rendu restait nulle sous prérendu partiel (saisie désactivée — résolution à la demande désormais) ; Realtime exige le jeton de session posé **avant** l'abonnement, sinon la RLS ne livre aucun événement au client cookie ; et l'événement d'insertion du brouillon consommait à tort le bip d'arrivée (déduplication séparée).
La requête de confirmation elle-même dure ~5 s (appels distants enchaînés) : sans effet sur l'apparition patron, mais à optimiser. Clés VAPID et CRON_SECRET générées dans `.env` ; l'e-mail de secours exige encore un compte Resend (RESEND_API_KEY / EMAIL_FROM) et n'a pas été envoyé en réel.
